# Архитектурные решения (ADR-lite)

Статусы: `proposed` — предложено, ждёт подтверждения; `accepted` — принято; `rejected`;
`superseded` — заменено другим решением; `deferred` — отложено.

Формат: решение → почему → альтернативы.

---

## D-001. Три модуля: UI, API, Worker; API и Worker — один пакет · `accepted`
Требование владельца. Worker запускается командой CLI того же пакета, логика не дублируется.
Связь API ↔ Worker только через БД.

## D-002. Python-стек backend · `accepted` (2026-10-18)
Python 3.14 (на ПК разработки нет 3.13, 3.14 — стабильная), uv, FastAPI, SQLAlchemy 2.1 async, Alembic, Pydantic v2, pydantic-settings,
Typer (CLI), logging. Инструменты: ruff (lint + format), mypy (strict для `domain/`),
pytest + pytest-asyncio.
**Почему:** FastAPI и aiogram асинхронные — единый async-стек без смешивания sync/async.

## D-003. СУБД: SQLite сейчас → PostgreSQL перед MVP · `accepted` (2026-10-18)
**Решение владельца:** разработку начинаем на SQLite (aiosqlite), перед запуском MVP
переезжаем на уже существующий сервер PostgreSQL (asyncpg).
**Как не создать себе проблем при переезде:**
- Только переносимые типы SQLAlchemy; никаких диалект-специфичных колонок (JSONB, ARRAY).
- Даты-время: SQLite не хранит TZ → свой `TypeDecorator` `UTCDateTime`, который всегда
  пишет/читает aware-datetime в UTC. В PostgreSQL ляжет в `timestamptz`.
- Alembic с `render_as_batch=True` (SQLite не умеет большинство `ALTER TABLE`).
- SQLite: `PRAGMA journal_mode=WAL`, `busy_timeout`, `foreign_keys=ON` при подключении
  (api и worker пишут одновременно).
- Защита от двойной отправки — через уникальный индекс `occurrence(routine_id, scheduled_for)`,
  а не через `FOR UPDATE SKIP LOCKED` (в SQLite его нет). Работает в обеих СУБД.
- Перенос данных: `pg_dump`-аналога нет → скрипт `reminder export/import` или просто
  перенос через SQLAlchemy (данных мало). Задача заведена в TASK.md.

## D-004. Telegram-библиотека: aiogram 3 · `accepted` (2026-10-18)
**Почему:** async-native, FSM для диалогов, inline-клавиатуры и callback-data фабрики.
**Альтернатива:** python-telegram-bot v21+ — тоже подходит, разница не принципиальна.

## D-005. Транспорт бота: long polling внутри процесса worker · `accepted` (2026-10-18)
**Почему:** домашний сервер, публичный HTTPS не нужен; один потребитель апдейтов на токен.
Scheduler loop и polling — две asyncio-задачи в одном процессе.

## D-006. Планировщик: «tick» по состоянию в БД (`next_run_at`) · `accepted` (2026-10-18)
**Почему:** идемпотентно, переживает рестарты, тестируемо, без внешних зависимостей.
**Отклонённые альтернативы:** APScheduler, Celery/RQ + beat.

## D-007. Формат расписания: RRULE (RFC 5545) · `accepted` (2026-10-18)
**Решение:** расписание рутины хранится как RRULE, считается через `python-dateutil` (`rrulestr`).
- Время в правиле (`BYHOUR`/`BYMINUTE`) — локальное время пользователя (`User.timezone`).
- `DTSTART` — дата создания рутины (точка отсчёта для `INTERVAL`), хранится вместе с правилом.
- Колонка `schedule_kind` (сейчас только `rrule`) оставлена для расширения.
- В боте и UI правило не вводится руками: выбираются пресеты/дни недели/время, строка RRULE
  собирается на бэкенде; API отдаёт и правило, и человекочитаемое описание.

**Почему не cron:** cron не выражает «каждые N дней» и «через неделю» (нет точки отсчёта,
`*/3` в днях месяца сбивается на границе месяца), плюс ловушка OR между днём месяца и
днём недели. RRULE покрывает всё это и тоже умеет перечислять срабатывания назад (`before()`)
для подсчёта серий.

## D-009. Серии считаются по запланированным occurrence · `accepted` (2026-10-18)

сегодняшний — нет.

## D-013. Аутентификация: в MVP её нет, в UI — селектор пользователя · `accepted` (2026-10-18)
- Пользователи создаются ботом при `/start` (если у чата есть доступ, D-020).
- UI: выпадающий список пользователей (`GET /api/v1/users`), выбор хранится в `localStorage`.
- Клиент передаёт выбранного пользователя заголовком `X-User-Id`. На бэкенде — одна
  зависимость FastAPI `get_current_user`.
- Позже вход через Telegram (Login Widget / Mini App `initData`): меняется только
  реализация `get_current_user`, роуты и UI-запросы остаются прежними.
- Безопасность: допустимо только потому, что сервер домашний и наружу не открыт.

## D-014. Осознанный пропуск (`skipped`) обрывает серию · `accepted` (2026-10-18)
Статус `skipped` всё равно хранится отдельно от «не выполнено» — для статистики и UI
(«пропущено осознанно» vs «забыл»). «Заморозки» серий нет.

## D-015. Повторных напоминаний нет · `accepted` (2026-10-18)
Одна отправка чек-листа на occurrence.

## D-016. Добавление привычек — интерактивной командой бота · `accepted` (2026-10-18)
`/add` запускает диалог (aiogram FSM) в одном сообщении, которое бот редактирует по шагам:
ввод названия → выбор рутины кнопками (или «➕ Новая рутина» → название → расписание
кнопками-пресетами) → подтверждение. UI в MVP — только чтение.

## D-018. Чек-лист можно отмечать до конца локальных суток · `accepted` (2026-10-18)
- Occurrence открыт до 23:59:59 своего `local_date` в TZ пользователя, затем закрывается
  (`closed_at` = начало следующих локальных суток, хранится в UTC).
- Нажатие кнопки в закрытом чек-листе → бот отвечает «День закрыт» (`answerCallbackQuery`),
  отметка не сохраняется; при закрытии бот снимает клавиатуру со старого сообщения.
- Закрытие ленивое: статус определяется сравнением `now()` с `closed_at`; отдельная задача
  в `tick()` только снимает клавиатуру и проставляет `closed`.
- Серия: открытый (сегодняшний) occurrence серию не рвёт; закрытый без `done` — рвёт.

## D-020. Доступ к боту хранится в БД, админка — в боте · `accepted` (2026-10-18)
Заменяет `TELEGRAM_ALLOWED_CHAT_IDS` из конфига.
- Таблица `chat_access` по `telegram_chat_id`: `pending` | `allowed` | `denied`, флаг `is_admin`.
  Ключ — чат, а не пользователь: доступ можно выдать до первого сообщения, а заявка
  существует раньше регистрации.
- Новый человек получает доступ двумя способами: пишет боту → заявка приходит всем админам с
  кнопками «Разрешить / Отклонить»; либо админ сам выполняет `/allow <chat_id>`.
- Команды админа в боте: `/admin`, `/users`, `/requests`, `/allow`, `/revoke`. Админы видят их
  в меню своего чата (scope `BotCommandScopeChat`, обновляется при старте worker).
- Первый админ и смена админов — через CLI `reminder admin grant | demote | list`.
  Последнего админа снять нельзя; себя и другого админа через `/revoke` закрыть нельзя.
- Отзыв доступа (`denied`) не удаляет данные: пользователь пропадает из UI, ему перестают
  приходить чек-листы; при возврате доступа пропущенные дни станут `missed` (не рвут серию).
- Веб-админка — позже, после входа через Telegram (без авторизации в UI это небезопасно).
